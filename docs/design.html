ClaimCheck: pre-submission claim assistant for Exchange4Health

Design sketch: components, responsibilities, interaction flows and the provider's experience.

Rules / code LLM Human decision Dashed = design only, not built for the demo
Design principle: code decides what is certain (dates, units, matching records), the LLM handles what is fuzzy (reading payer documents, contract rules, explaining and suggesting fixes), and a person approves anything that changes money or rules.

1. System overview

Three engines share two stores. The Predictor checks each claim before submission. The Monitor watches outcomes and payer portals over time. The Rule pipeline turns payer documents into an approved, versioned rule table. The Monitor and Predictor never talk to each other directly: they communicate through the Rule table and the Claim ledger, so every change is approved and auditable.

3. Predictor: checking a batch of claims

The provider uploads a batch; the predictor works through it one claim at a time and returns a single results table. Claims are processed in submitted_date order so authorization balances, duplicates and daily totals are correct. The rule engine runs first; the LLM only sees the facts the code has already worked out.

5. Monitor: watching trends and rule changes

The Monitor never changes the rule table or contacts providers on its own: it drafts, and a person approves.

6. Claim lifecycle and the ledger

Every state change updates the ledger, which keeps authorization balances and claim groups current for the next prediction. Submitted-but-undecided claims hold units, so two claims cannot both appear to fit the same remaining balance.
